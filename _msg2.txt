Make every command work the same on containers and root-access VMs

Each server records which backend it runs on. Operations route to the right
hypervisor instead of always shelling out to Docker, so a Docker container
and a full KVM machine can be handed out from the same host at the same
time and every command behaves the same on both.

Lifecycle and control
- container_op dispatches to libvirt or Incus for non-container servers, so
  start, stop, restart, resize, ping, ports and uptime already work everywhere
- reinstall, reinstallos, delete_vps, backupvps and restorevps no longer call
  docker directly. They go through teardown_instance, rebuild_instance,
  create_backup and restore_backup, which each pick the right mechanism:
  docker commit/run, virsh snapshot, or incus export/import
- delete_backup removes the right artifact per backend rather than always
  calling docker rmi

File management
- !upload and !download use docker cp for containers, incus file push/pull
  for LXC, and tell the customer to use scp for a full VM, because the host
  cannot read a VM disk without a guest agent
- !files, !cat, !mkdir and !rmfile now report failures. They previously
  ignored the exit code and announced success even when the command failed,
  and !mkdir and !rmfile reported success on a server where exec is
  impossible at all
- !rmfile refuses to delete core system paths

Ports
- !portadd and !portremove apply immediately on a KVM VM by redefining the
  domain, instead of saying "published on the next reinstall" and quietly
  doing nothing until the customer reinstalled. The reply now states that a
  restart is required for the forwards to take effect
- Blocked host ports are enforced in the KVM XML builder as well as in
  !portadd, so no code path can publish the Docker API or a database port

Password resets
- !resetpass works on full virtual machines. The host rebuilds the cloud-init
  seed with the new password and a new instance-id, which makes cloud-init
  re-run its config stage on the next boot, then reboots the VM
- !resetpass previously failed outright on any non-Docker server

Safety
- restore_vps looked up its record with an inner loop whose break did not exit
  the outer loop, so it could pick the wrong server on a name collision. It
  now uses find_vps_by_name and reports a real error when the name is unknown
- A failed restore now reports through the progress screen instead of a
  separate message that could be swallowed by the confirmation view

Tests
- 51 checks, up from 45. New coverage: cross-backend coexistence, legacy
  records without a virt field still resolving to Docker, VM disks living
  outside Docker's storage, and clean failure when redefining a missing
  domain
